# Практические работы по дисциплине «Фронтенд и бэкенд разработка»

Практические задания разделены по веткам репозитория.

В результате выполнения второй контрольной работы (практические 19 - 23) были выполнены следующие задания, посвященные добавлению баз данных (SQL и NoSQL), балансировке и контейнеризации:

## Практическое задание 19
В рамках данного практического задания был разработан полноценный REST API бэкенд на базе фреймворка Express.js. Основной акцент был сделан на реализацию базовых CRUD-операций для управления сущностью «Пользователь». В качестве основного хранилища реляционных данных была выбрана СУБД PostgreSQL. Для взаимодействия с базой данных на уровне кода применялась библиотека Sequelize ORM, что позволило описывать структуру таблиц в виде JavaScript-моделей. В процессе работы были настроены схемы данных, включающие строгую валидацию полей на уровне базы данных и самого приложения. Также была реализована централизованная логика обработки ошибок, позволяющая возвращать клиенту понятные HTTP-статусы и JSON-сообщения. Дополнительно настраивалось безопасное подключение к БД через скрытые переменные окружения `.env`. Итоговый API поддерживает создание, чтение, обновление и удаление записей пользователей, обеспечивая надежный фундамент для дальнейшего масштабирования бизнес-логики проекта.

## Практическое задание 20
Данная работа была посвящена изучению и внедрению NoSQL подходов к хранению информации в веб-приложениях. Часть бэкенда, отвечающая за управление пользователями, была полностью переписана для работы с документоориентированной базой данных MongoDB. Переход от жестких реляционных таблиц к гибким JSON-подобным документам потребовал пересмотра структуры хранимых данных. Для удобной интеграции с приложением использовалась библиотека Mongoose, позволившая задать строгие схемы (Schemas) на уровне кода, сохраняя при этом гибкость NoSQL. Были переработаны все контроллеры и сервисы, чтобы корректно выполнять асинхронные запросы к коллекции MongoDB. Также на практике исследовались механизмы работы с уникальными идентификаторами (ObjectId) и обработки вложенных структур данных. Опыт перехода с PostgreSQL на MongoDB позволил наглядно оценить различия между SQL и NoSQL базами данных в контексте производительности и удобства разработки. В результате приложение получило легко масштабируемое хранилище, отлично подходящее для работы с неструктурированными или часто меняющимися данными.

## Практическое задание 21
Для существенного повышения производительности и скорости отклика сервера в архитектуру приложения был внедрен in-memory кэш на базе Redis. Основной задачей стало снижение нагрузки на основную базу данных за счет кэширования результатов часто выполняемых и ресурсоемких запросов. Был настроен клиент Redis, который устанавливает постоянное соединение с сервером кэширования при старте приложения. В исходный код были добавлены специализированные middleware-функции, перехватывающие входящие GET-запросы и проверяющие наличие готовых ответов в оперативной памяти. Для различных типов данных, таких как списки товаров или профили пользователей, были заданы оптимальные значения времени жизни кэша (TTL - Time To Live). Особое внимание уделялось стратегиям инвалидации: при любом изменении, добавлении или удалении данных через POST/PUT/DELETE запросы соответствующие ключи в Redis принудительно очищаются. Это гарантирует, что клиенты всегда получают только актуальную информацию без риска рассинхронизации. В результате внедрения Redis среднее время ответа сервера многократно сократилось, что критически важно для высоконагруженных систем.

## Практическое задание 22
Данный этап был сфокусирован на обеспечении высокой доступности и отказоустойчивости приложения посредством горизонтального масштабирования. В качестве мощного балансировщика нагрузки и обратного прокси-сервера (reverse proxy) был развернут и настроен веб-сервер Nginx. Архитектура приложения была изменена таким образом, чтобы одновременно работали несколько независимых экземпляров бэкенда на разных сетевых портах. В конфигурационном файле `nginx.conf` был описан блок `upstream`, объединяющий эти рабочие экземпляры в единый пул серверов. Nginx был настроен на равномерное распределение входящего клиентского HTTP-трафика между серверами с использованием классического алгоритма Round Robin. Дополнительно прописывались служебные директивы для корректной передачи исходных HTTP-заголовков, таких как реальный IP-адрес клиента (`X-Real-IP`) и запрошенный хост. Для наглядной демонстрации работы балансировки каждый бэкенд был модифицирован так, чтобы возвращать свой уникальный идентификатор (`SERVER_ID`) в теле ответа корневого маршрута. Проведенное ручное тестирование подтвердило, что при выходе из строя одного из узлов система продолжает корректно обслуживать пользователей, перенаправляя трафик на оставшиеся рабочие серверы.

## Практическое задание 23
Итоговая практическая работа объединила все предыдущие этапы путем полной контейнеризации микросервисного проекта с использованием экосистемы Docker. Для каждого компонента системы, включая бэкенд на Node.js и фронтенд-приложение на React/Vite, были написаны оптимизированные сценарии сборки `Dockerfile`. Сборка фронтенда была реализована через продвинутый паттерн multi-stage build, где финальный образ содержит только легковесный веб-сервер Nginx и статичные скомпилированные файлы бандла. Для удобной оркестрации многоконтейнерной среды был создан конфигурационный файл `docker-compose.yml`, описывающий одновременный запуск балансировщика, трех независимых реплик бэкенда и сервиса кэширования Redis. Все развернутые сервисы были помещены в единую изолированную виртуальную сеть `app-network`, что исключило необходимость проброса лишних портов на хост-машину и значительно повысило безопасность стека. В коде приложения адреса подключения к сервисам были адаптированы для работы во внутренней DNS-сети Docker, окончательно отказавшись от использования `localhost`. Конфигурация Nginx была дополнена параметрами `max_fails` и `fail_timeout` для автоматического обнаружения сбоев (Circuit Breaker) и исключения недоступных контейнеров из пула балансировки. Теперь комплексное развертывание всего сложного микросервисного стека с базами, кэшем и прокси осуществляется в любой среде буквально одной командой `docker compose up --build`.
